# Git у проєкті claude-store

Практична пам'ятка під цей конкретний проєкт. Не підручник — тільки те, що
реально знадобиться щодня.

---

## 1. Що під версійним контролем

Репозиторій — це **папка теми**, а не весь сайт (ADR-007 у [DECISIONS.md](DECISIONS.md)).

```
корінь репозиторію:
  /Users/admin/Local Sites/claude-store/app/public/wp-content/themes/my-theme
```

| Під git | Поза git |
|---|---|
| PHP-шаблони теми | ядро WordPress |
| SCSS і **зібраний CSS** | плагіни |
| JS, зображення теми | `wp-content/uploads` |
| `docs/` | база даних |
| `package.json` | `node_modules/` |

**Чому зібраний CSS теж комітимо:** на хостингу може не бути Node, і деплой має
зводитись до `git pull` без кроку збірки (ADR-008). Карти джерел `.css.map` —
навпаки, лише локальні, вони в `.gitignore`.

## 2. Як ми працюємо

| Хто | Команди |
|---|---|
| Claude | `status`, `log`, `diff`, `branch` — тільки читання, щоб бачити стан |
| Ти | `add`, `commit`, `merge` — усе, що змінює історію |

Claude завжди спершу перевіряє, **що саме потрапить у коміт**, і лише потім
диктує команду.

## 3. Щоденний цикл

```bash
cd "/Users/admin/Local Sites/claude-store/app/public/wp-content/themes/my-theme"

git status                  # що змінилось
git diff                    # що саме змінилось у коді
npm run build               # ⚠ перед комітом — перезібрати CSS

git add inc/enqueue.php     # додати конкретні файли
git commit -m "fix(shop): …"
git push
```

**Чому `git add` конкретними файлами, а не `git add .`**

`git add .` заганяє в коміт усе підряд — зокрема випадкові правки й тимчасові
файли. Коміт із назвою «фікс кошика», у якому лежать ще чотири сторонні зміни,
неможливо відкотити окремо. Додавай те, що стосується задачі.

Якщо змін багато й усі по темі — можна `git add -A`, але спершу глянь `git status`.

## 4. Повідомлення комітів

Формат — Conventional Commits, опис українською:

```
feat(cart): фільтр каталогу за атрибутами
fix(checkout): валідація телефону приймала літери
refactor(scss): токени кольорів винесено в abstracts
chore(deps): оновлено sass до 1.80
docs: чекліст фази 4
style(header): вирівнювання іконки кошика
perf(catalog): транзієнт для хітів продажів
```

| Тип | Коли |
|---|---|
| `feat` | нова можливість |
| `fix` | виправлення помилки |
| `refactor` | код змінено, поведінка та сама |
| `style` | тільки оформлення, без логіки |
| `perf` | швидкодія |
| `docs` | документація |
| `chore` | збірка, залежності, службове |

**Правила:**

- один коміт — одна логічна зміна
- заголовок до 72 символів, наказовий спосіб: «додай», а не «додав»
- не комітити зламаний код у `main`

Довге повідомлення пишеться так:

```bash
git commit
```

Відкриється редактор: перший рядок — заголовок, порожній рядок, далі опис.
Зберегти й вийти: `:wq` у Vim або `Ctrl+O`, `Enter`, `Ctrl+X` у nano.

## 5. Гілки

### Модель проєкту

| Гілка | Призначення |
|---|---|
| `main` | продакшн. Завжди робоча, тегується релізами |
| `dev` | основна робота. Мерж у `main` = готовність до релізу |
| `feat/*`, `fix/*` | велика окрема задача, мерж у `dev` |

Поки проєкт один і розробник один, можна працювати прямо в `dev`, а окремі
гілки заводити лише під ризиковані зміни — щоб було куди відступити.

### Створити гілку

```bash
git switch -c feat/checkout      # створити й одразу перейти
```

Стара форма `git checkout -b feat/checkout` робить те саме. `switch` з'явився
пізніше й робить лише одну річ, тому помилитись важче.

### Перемикатись

```bash
git switch dev                   # перейти на наявну
git switch -                     # назад на попередню
git branch                       # список локальних, зірочка = поточна
```

⚠️ Перед перемиканням робоче дерево має бути чистим. Якщо є незакомічені зміни —
або закоміть, або сховай (див. нижче).

### Тимчасово сховати зміни

```bash
git stash                        # прибрати зміни «в кишеню»
git switch main
# …щось зробив…
git switch dev
git stash pop                    # повернути з кишені
```

### Видалити гілку

```bash
git branch -d feat/checkout      # тільки якщо вже влита
git branch -D feat/checkout      # примусово, зміни втрачаються
```

## 6. Мердж

Влити `dev` у `main`:

```bash
git switch main                  # 1. стати НА ту гілку, куди вливаємо
git merge dev                    # 2. влити ту, звідки беремо
git push
```

Головне правило, яке всі плутають: **спершу переходиш туди, КУДИ вливаєш**.
`git merge dev` на гілці `main` означає «додай мені зміни з dev».

### Що буде на екрані

- **Fast-forward** — у `main` не було власних змін, git просто пересунув
  вказівник. Найкращий випадок
- **Merge commit** — обидві гілки змінювались, git створив коміт злиття.
  Відкриється редактор із готовим текстом, просто збережи
- **CONFLICT** — git не зміг вирішити сам, див. наступний розділ

## 7. Конфлікти

Конфлікт виникає, коли **той самий рядок** змінили у двох гілках. Git не вгадує —
питає тебе.

У файлі з'явиться таке:

```
<<<<<<< HEAD
$color-primary: #5b9bc4;
=======
$color-primary: #4a90b8;
>>>>>>> dev
```

- між `<<<<<<< HEAD` і `=======` — версія гілки, **на якій ти стоїш**
- між `=======` і `>>>>>>> dev` — версія гілки, яку **вливаєш**

### Як вирішити

1. Відкрий файл, прибери маркери `<<<<<<<`, `=======`, `>>>>>>>` і лиши
   потрібний код. Можна взяти шматок з обох
2. `git add файл` — так ти кажеш «конфлікт вирішено»
3. `git commit` — завершує мердж

Подивитись, які файли в конфлікті:

```bash
git status
git diff --name-only --diff-filter=U
```

Передумав посеред мерджу:

```bash
git merge --abort            # повернутись у стан до мерджу
```

### ⚠️ Конфлікт у `assets/css/`

Це **згенеровані** файли. Розбирати їх руками безглуздо — просто перезбери:

```bash
git checkout --ours assets/css/style.css     # взяти будь-яку версію
npm run build                                 # і перезаписати збіркою
git add assets/css/
```

Правило: конфлікт у `assets/css/*` вирішується `npm run build`, а не редактором.

## 8. Відкат

Найважливіший розділ. Ситуації різні — команди теж.

### Ще не додано в індекс

```bash
git restore inc/enqueue.php       # відкотити один файл
git restore .                     # відкотити всі зміни
```

### Уже зробив `git add`, але не комітив

```bash
git restore --staged inc/enqueue.php   # прибрати з індексу, зміни лишаться
git restore inc/enqueue.php            # і скасувати самі зміни
```

### Закомітив, але не запушив

```bash
git commit --amend                # переписати ОСТАННІЙ коміт (текст або вміст)
git reset --soft HEAD~1           # скасувати коміт, зміни лишити в індексі
git reset --mixed HEAD~1          # скасувати коміт, зміни лишити у файлах
git reset --hard HEAD~1           # ⚠ скасувати коміт І видалити зміни
```

### Уже запушив

Переписувати опубліковану історію не можна — робимо зворотний коміт:

```bash
git revert <хеш>                  # створює новий коміт, який скасовує старий
```

Знайти хеш: `git log --oneline`

### Повернути один файл зі старого коміту

```bash
git checkout <хеш> -- woocommerce/cart/cart.php
```

### Все пропало

```bash
git reflog                        # історія ВСІХ переміщень, навіть «втрачених»
git reset --hard <хеш звідти>
```

`reflog` рятує майже завжди — git не видаляє коміти одразу.

## 9. Історія

```bash
git log --oneline -10                    # останні 10 комітів коротко
git log --oneline --graph --all          # з гілками, візуально
git log -p woocommerce/cart/cart.php     # історія одного файлу зі змінами
git show <хеш>                           # що саме змінив коміт
git blame inc/enqueue.php                # хто і коли писав кожен рядок
```

`git blame` — не про пошук винних, а про пошук **коміту**: бачиш рядок, дізнаєшся
хеш, читаєш повідомлення й розумієш, навіщо це писали.

## 10. Релізи

```bash
git switch main
git merge dev
git tag -a v1.0.0 -m "Перший реліз"
git push origin main --tags
```

Версії семантичні: `v1.2.3` — мажорна.мінорна.патч.

| Що змінилось | Яку цифру піднімати |
|---|---|
| виправлення | патч → `v1.0.1` |
| нова можливість | мінорна → `v1.1.0` |
| несумісні зміни | мажорна → `v2.0.0` |

Кожен реліз записуємо в [PROGRESS.md](PROGRESS.md), розділ «Релізи».

## 12. Типові ситуації

**«Закомітив не той файл»**
```bash
git reset --soft HEAD~1      # коміт скасовано, зміни в індексі
git restore --staged зайвий-файл
git commit -m "…"            # комітимо тільки потрібне
```

**«Помилка в тексті коміту»**
```bash
git commit --amend -m "правильний текст"
```
Тільки якщо ще **не** запушив.

**«Забув перезібрати CSS перед комітом»**
```bash
npm run build
git add assets/css/
git commit --amend --no-edit    # доклеїти до попереднього коміту
```

**«Треба терміново правити прод, а я посеред задачі»**
```bash
git stash
git switch main
# правиш, комітиш, пушиш
git switch dev
git stash pop
```

**«Випадково закомітив `node_modules`»**
```bash
git rm -r --cached node_modules
git commit -m "chore: прибрати node_modules з репозиторію"
```
Файли на диску лишаться, з git — зникнуть. `.gitignore` уже налаштований, тож
повторно вони не потраплять.

**«Хочу побачити, що зміниться перед pull»**
```bash
git fetch
git log HEAD..origin/main --oneline
```

## 13. Чого не робити

| Не роби | Чому |
|---|---|
| `git push --force` у `main` | перепише історію в усіх, хто вже забрав |
| `git add .` не глянувши `git status` | у коміт заїде випадкове |
| комітити ключі, паролі, токени | з історії їх прибирати дуже боляче |
| комітити зламаний код у `main` | `main` має бути готова до деплою будь-якої миті |
| один величезний коміт за день | неможливо відкотити частину |
