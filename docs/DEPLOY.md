# Деплой і хостинг — claude-store

---

## 1. Вибір хостингу

Хостинг ще не обрано. Нижче — критерії та рекомендація.

### 1.1 Мінімальні вимоги

Магазин на 100–1000 товарів з варіаціями — це не блог. Дешевий шаред за 2 $ ляже в перший
же день розпродажу.

| Параметр | Мінімум | Бажано |
|---|---|---|
| PHP | 8.2 | 8.3 |
| MySQL / MariaDB | 8.0 / 10.6 | останні |
| Пам'ять PHP | 256 МБ | 512 МБ |
| `max_execution_time` | 120 с | 300 с (імпорт каталогу) |
| `upload_max_filesize` | 64 МБ | 128 МБ |
| Диск | 10 ГБ SSD | 20 ГБ NVMe |
| SSL | Let's Encrypt безкоштовно | те саме |
| SSH + wp-cli | **обов'язково** | те саме |
| Redis / Memcached | бажано | обов'язково при 1000+ SKU |
| Бекапи | щоденні, 30 днів | + свої в зовнішнє сховище |
| Staging | бажано | обов'язково |
| HTTP/2, Brotli | так | так |

**Червоні прапорці:** немає SSH · PHP 7.x · «безлімітний» тариф за копійки ·
немає бекапів · немає staging · заборонений `wp-cron` без альтернативи.

### 1.2 Рекомендація

**Основний варіант — керований VPS (Cloudways на Hetzner/DigitalOcean, або аналог).**

Чому:

- Ціна ~14–25 $/міс за 2 ГБ RAM — на рівні хорошого шареду, але ресурси твої
- Staging в один клік, Redis з коробки, SSH і wp-cli, git-деплой
- Сервером не адмініструєш сам — оновлення й безпека на провайдері
- Вертикальне масштабування без міграції: клік — і 4 ГБ

Мінус: оплата картою в доларах, підтримка англійською, серверна юрисдикція поза Україною.

**Альтернатива — український хостинг (Hostiq, Ukraine.com.ua, Cityhost).**

Коли обирати: замовнику потрібні документи (акт, ФОП, оплата в UAH), українська підтримка,
дані в українській юрисдикції. Брати **VPS або старший тариф із SSH**, не базовий шаред.

Мінус: менше автоматизації, staging часто відсутній або платний.

**Чого не брати:** найдешевший шаред без SSH · хостинг «з конструктором сайтів» ·
Kinsta/WP Engine (від 30 $ і вище — виправдано на трафіку, якого поки немає).

## 2. Середовища

| Середовище | Призначення | URL | Гілка git |
|---|---|---|---|
| Локальне | Розробка | `claude-store.local` | `dev` |
| Staging | Перевірка перед релізом | `staging.домен` | `dev` |
| Продакшн | Бойовий сайт | `домен` | `main` |

**Правила:**

1. На проді нічого не правимо через файловий менеджер. Ніколи. Зміна → git → деплой.
2. Редактор коду в адмінці вимкнено (`DISALLOW_FILE_EDIT`).
3. Staging закрито від індексації і паролем на рівні сервера.
4. Платіжки на staging — **тільки в тестовому режимі**.
5. База на staging — копія проду з **знеособленими** персональними даними покупців.

### Доступи

Паролі — **тільки в менеджері паролів** (Bitwarden / 1Password). Не в git, не в месенджері,
не в цьому файлі. Тут лише перелік, що де лежить.

| Доступ | Де зберігається | У кого є |
|---|---|---|
| Панель хостингу | — | — |
| SSH / SFTP | — | — |
| База даних | — | — |
| WP-адмін (прод) | — | — |
| Реєстратор домену / DNS | — | — |
| Мерчант платіжки | — | — |
| API Нової Пошти | — | — |
| SMTP-сервіс | — | — |
| Git-репозиторій | — | — |

## 3. Що деплоїмо

**Під git тільки тема** (`wp-content/themes/my-theme`) плюс, за потреби, `mu-plugins`.

Ядро WordPress, плагіни, `wp-content/uploads` і база **не в git**. Ядро й плагіни
оновлюються через адмінку/wp-cli, медіа синхронізується окремо.

Чому не «весь сайт у git»: `uploads` роздує репозиторій до гігабайтів, а плагіни
мають власний механізм оновлення. Composer-підхід (wpackagist) розглянемо, якщо
кількість плагінів переросте 15 — записати в [DECISIONS.md](DECISIONS.md).

## 4. Перший реліз: покроково

### Крок 1. Підготовка локально

```bash
cd "/Users/admin/Local Sites/claude-store/app/public/wp-content/themes/my-theme"

npm run build          # мініфікований CSS без source-map
git status             # робоче дерево чисте?
git checkout main && git merge dev
git tag v1.0.0
git push origin main --tags
```

- [ ] Групи полів SCF експортовані в Local JSON і закомічені
- [ ] У `assets/css/` лежить свіжий зібраний CSS
- [ ] Немає закомічених ключів, паролів, `console.log`, `var_dump`

### Крок 2. Хостинг і домен

- [ ] Тариф оплачено, сервер створено
- [ ] PHP 8.2+ обрано в панелі
- [ ] Домен делеговано на NS хостингу (**зміна DNS діє до 24–48 год** — робити заздалегідь)
- [ ] A-запис на IP сервера, `www` → CNAME
- [ ] SSL (Let's Encrypt) випущено, автопродовження увімкнено
- [ ] Примусовий HTTPS

### Крок 3. Перенесення бази й медіа

Через SSH — надійніше за плагіни міграції:

```bash
# ЛОКАЛЬНО (Local → Open site shell)
wp db export ../claude-store.sql
tar -czf ../uploads.tar.gz wp-content/uploads

# завантажити обидва файли на сервер (scp/sftp)

# НА СЕРВЕРІ
wp db import claude-store.sql
wp search-replace 'http://claude-store.local' 'https://домен' --all-tables --precise --report-changes-only
wp search-replace '//claude-store.local' '//домен' --all-tables --precise
tar -xzf uploads.tar.gz -C wp-content/
```

🔴 `search-replace` через wp-cli, **не через SQL `REPLACE`** — у базі є серіалізовані
масиви (налаштування Woo, віджети), звичайний REPLACE ламає їх довжину і поле мовчки
перестає читатись.

- [ ] Резервна копія бази **до** імпорту
- [ ] Після заміни перевірити: `wp option get siteurl` і `home`
- [ ] `wp cache flush`, `wp rewrite flush`

Альтернатива без SSH: плагін міграції (All-in-One WP Migration / Duplicator). Повільніше
й з ризиком тайм-ауту на великій базі, але робочий варіант для шареду.

### Крок 4. Тема й плагіни

- [ ] Тему залити: `git clone` на сервері (якщо є SSH) або SFTP-вивантаженням папки
- [ ] `node_modules/` **не заливати**
- [ ] Плагіни встановити з нуля через адмінку/wp-cli, не копіювати папками
- [ ] Ліцензійні ключі преміум-плагінів активувати на бойовому домені
- [ ] Тему активовано, помилок немає

### Крок 5. Конфігурація проду

У `wp-config.php`:

```php
define( 'WP_DEBUG', false );
define( 'WP_DEBUG_LOG', false );
define( 'WP_DEBUG_DISPLAY', false );
define( 'DISALLOW_FILE_EDIT', true );
define( 'WP_AUTO_UPDATE_CORE', 'minor' );
define( 'WP_MEMORY_LIMIT', '256M' );
define( 'WP_POST_REVISIONS', 5 );
define( 'EMPTY_TRASH_DAYS', 7 );
```

- [ ] 🔴 **Нові солі й ключі** — згенерувати на `api.wordpress.org/secret-key/1.1/salt/`. Локальні на прод не переносимо
- [ ] Префікс таблиць не `wp_`, якщо є можливість змінити безболісно 🔵
- [ ] Права: файли 644, папки 755, `wp-config.php` 600
- [ ] Вимкнути `wp-cron` у конфізі й повісити системний cron кожні 5 хв 🟡 (інакше кожен візит смикає крон)

### Крок 6. Бойові інтеграції 🔴

- [ ] Ключі платіжного шлюзу — з тестових на **бойові**
- [ ] Тестовий режим шлюзу вимкнено
- [ ] API-ключ Нової Пошти бойовий
- [ ] SMTP налаштовано на бойовий домен, SPF/DKIM/DMARC у DNS
- [ ] ПРРО (якщо потрібне) підключено до реальної каси
- [ ] Реквізити ФОП/ТОВ у підвалі й офері — справжні

### Крок 7. Перевірка після релізу

- [ ] 🔴 **Налаштування → Читання → зняти «Попросити пошукові системи не індексувати»**
- [ ] Головна, каталог, картка товару, кошик, оформлення відкриваються
- [ ] Зображення вантажаться (не битий шлях після міграції)
- [ ] Пошук і фільтри працюють
- [ ] 🔴 **Реальне тестове замовлення з оплатою на 1 ₴** — гроші реально списались і повернулись
- [ ] Лист про замовлення прийшов покупцю **і** адміну, не в спам
- [ ] HTTPS без mixed content (консоль браузера)
- [ ] 404-сторінка працює
- [ ] `robots.txt` і `sitemap.xml` доступні
- [ ] PageSpeed на проді (числа відрізняються від локальних)
- [ ] Search Console: домен підтверджено, sitemap відправлено
- [ ] Логи сервера за першу годину — без 500-х

### Крок 8. Захист і бекапи

- [ ] Бекапи налаштовані: щоденно база, щотижня файли, зберігання 30 днів
- [ ] 🔴 **Відновлення перевірено на staging** — бекап, який ніколи не відновлювали, не бекап
- [ ] Копія в зовнішнє сховище (S3/Backblaze), не тільки на тому ж сервері
- [ ] Захист `wp-login.php`: обмеження спроб + 2FA для адмінів
- [ ] Плагін безпеки, базове сканування
- [ ] Моніторинг доступності (UptimeRobot) з нотифікацією
- [ ] Обліковий запис адміна — не `admin`, пароль з менеджера

## 5. Наступні релізи (тільки тема)

```bash
# ЛОКАЛЬНО
git checkout dev
npm run build
git add -A && git commit -m "feat: опис зміни"
git push origin dev

# STAGING: розгорнути dev, перевірити
# → якщо ок:

git checkout main && git merge dev && git push origin main
git tag v1.1.0 && git push --tags

# НА ПРОДІ
cd wp-content/themes/my-theme && git pull origin main
wp cache flush
```

- [ ] Перед пулом на проді — бекап
- [ ] Після пулу — перевірити ключові сторінки й наскрізний сценарій купівлі
- [ ] Реліз у робочий час, не в п'ятницю ввечері
- [ ] Запис у [PROGRESS.md](PROGRESS.md)

## 6. Відкат

Якщо після релізу зламалось:

```bash
# 1. Відкотити код теми
cd wp-content/themes/my-theme
git log --oneline -5
git reset --hard <хеш попереднього робочого коміту>
wp cache flush

# 2. Якщо ламала база — відновити з бекапу
wp db import backup-YYYY-MM-DD.sql
```

- Спершу **зупинити кровотечу** (відкат), потім розбиратись у причині
- Причину й вирішення записати в [PROGRESS.md](PROGRESS.md) — розділ «Інциденти»

## 7. Регламент оновлень

| Що | Як часто | Порядок |
|---|---|---|
| Ядро WP (мінорні) | автоматично | — |
| Ядро WP (мажорні) | вручну, за 2 тижні після виходу | staging → перевірка → прод |
| **WooCommerce** | вручну, **автооновлення вимкнено** 🔴 | staging → перевірка **оверрайдів шаблонів** → прод |
| Платіжні плагіни | вручну | staging + тестова оплата → прод |
| Інші плагіни | раз на місяць | бекап → оновити → перевірити |
| Тема | за потребою | через git |

🔴 **Автооновлення WooCommerce має бути вимкнене.** Мажорний реліз Woo змінює шаблони,
а наші оверрайди в `woocommerce/` лишаються старими — магазин ламається без попередження
о третій ночі. Перелік оверрайдів ведемо в [DECISIONS.md](DECISIONS.md) і звіряємо при
кожному оновленні.
